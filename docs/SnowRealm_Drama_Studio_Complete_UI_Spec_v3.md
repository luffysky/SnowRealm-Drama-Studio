# SnowRealm Drama Studio V1｜完整 UI 與工程交付規格

> **整合修訂版 3.0（2026-11-03，B+ 導覽與120集規模修訂）**。取代舊版53張編號：01–23主頁面＋24–80逐張編號互動設計，共80張。這是設計／工程規格，**不代表已完成程式**；部分額外Tab尚未單獨繪圖。

## 0｜已確認決策

- **暖寶：CEO／製作總負責人；Luffysky：技術總監 CTO**。兩個真人帳號、均為Owner；只有帳密登入，無公開註冊與邀請。帳密由部署初始化安全產生。
- Next.js App Router＋TypeScript＋Tailwind＋Vercel；**Neon PostgreSQL**資料庫，**Cloudflare R2私有Bucket**素材；建議Drizzle ORM。
- V1是雙人AI短劇創作管理：小說→劇本→世界觀／角色→分鏡→素材→審核→外部後製。**不內建剪輯器、不公開播放、不自動發布第三方平台**。
- 《一灶見山河》規劃120集、單集120–180秒。許山河、前世、穿越、失憶、梅花印記是既定故事線索；**女主正式姓名：沈知味**。圖中「林婉兒」「小灶房」、王朝名稱、集數標題均是示意，不能自動當正史。
- AI只有在真正接通供應商API後才能執行；Claude Max或ChatGPT訂閱不等於API額度；生成前預估成本，結果先候選後人工採用。
- UI維持深色紫藍霓虹玻璃風；示意圖的費用、日期、進度、人物、模型連線不可寫死。

## 6｜R2 與安全實作

1. R2 使用私有 Bucket；瀏覽器以短效簽署 URL 直傳，完成後回報伺服器確認物件存在，Neon 才標記成功。大型影片使用 multipart upload；失敗可重試。
2. 原始素材與裁切、縮圖、去背等衍生素材分別保存。物件刪除前檢查 `asset_links` 引用與回收保留期；不可因刪除一筆資料庫紀錄就刪除共用檔案。
3. 密碼使用 Argon2id 等安全雜湊；HttpOnly/Secure/SameSite Session Cookie、登入限速、CSRF 防護、可撤銷工作階段。後端執行所有權限檢查，隱藏按鈕不等於授權。
4. API Key 不得明文存 Neon、瀏覽器或日誌；使用伺服器密鑰管理／加密。供應商連線狀態必須來自真實測試。
5. 版本快照不可變；還原舊版應建立新版本；已定稿內容必須透過審核解鎖或建立修訂版。
6. AI 工作需要持久化背景 Worker／Queue、冪等鍵、速率限制、指數退避、供應商結果查詢、取消與人工重試。重試不得盲目重複扣費；取消不保證供應商停止計費。
7. 費用控制在伺服器端攔截新付費任務；預估與已實際發生費用分開紀錄。


作品級 `/novel` 是索引入口，單集編輯器保留既有 `/episodes/[episodeId]/novel`；不得造成兩份正文。其他舊頁面路由可保留為深層功能，但必須由相應作品 Tab 進入。既有 `/projects/[projectId]/progress` 若已公開使用，做 308 轉址至 `/production`，勿直接刪除導致書籤失效。

**實作：** `src/app/(studio)/projects/[projectId]/layout.tsx` 載入作品、驗證登入者對該作品的權限，提供 `ProjectWorkspaceLayout`／`ProjectTabs`；全域 `AppShell` 只渲染一次。`projectId` 從路由參數取得，絕不可依賴 localStorage 或最後選擇作品。`resolveLeaf()` 僅供遷移過渡，不作為正式解析方式。作品切換時保留可映射的 Tab，否則返回目標作品總覽；不可把上一部作品的 episodeId 帶到下一部。

### 11.2 120集與1080階段紀錄的資料契約

- 《一灶見山河》目前目標 **120集 × 9階段 = 1,080筆階段紀錄**；這是計畫規模，**不是已完成紀錄數，也不是所有作品的硬性上限**。
- 九階段固定鍵：`story_planning`, `novel`, `script`, `storyboard`, `assets`, `video`, `postproduction`, `review`, `release`。UI 名稱依序：劇情規劃、小說創作、劇本改編、分鏡設計、素材製作、影像製作、後製剪輯、審核調整、上架發布。V1 不內建剪輯器或自動發布，相關階段可記錄外部完成狀態與憑證。
- `episode_production_stages` 至少有 `id`, `project_id`, `episode_id`, `stage_key`, `status`, `progress_percent`, `assignee_type`, `assignee_id`, `started_at`, `completed_at`, `approved_version_id`, `updated_at`，並設 `UNIQUE(episode_id, stage_key)`；另用 `production_progress_events` 保留變更稽核。
- 狀態建議 `not_started / in_progress / blocked / in_review / completed`。完成狀態必須對應必要驗收，不能只靠人工修改前端數字；`completed` 計1，`in_progress` 依已驗證的進度百分比計0～1，未開始／阻塞依已確認工作量計算，不能把阻塞直接當完成。等權重九階段是 V1 預設，後續若改權重需版本化計算規則。
- 對集數進度以 `SUM(stage_progress_fraction)/9` 計算，跨作品則以所有有效階段的已完成當量除以有效階段數；計算與四捨五入統一在後端。作品／集數是否封存、尚未建立階段時的分母規則要明確且一致。
- `production_milestones` 記錄批次目標，`production_dependencies` 記錄任務依賴，`production_progress_events` 記錄修改歷史。所有查詢以 `project_id` 限定，後端 RBAC 不得只依賴 UI 篩選。
