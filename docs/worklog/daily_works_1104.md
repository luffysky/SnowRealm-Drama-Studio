## 協定層面的兩個洞

這兩個不是打錯字，是設計時沒想到的情況。

### 收回／編輯不會即時同步

原本的即時協定只有一句話：「比這個序號新的給我」。
那處理新增沒問題，**處理不了修改**——收回不會改 `seq`
（改了訊息會跳到對話最底下，是錯的），所以對方永遠收不到。

加 `messages.updated_at`，串流改成抓「seq 比較新 **或** 這次同步之後被改過」。
實測：新訊息 196ms、編輯 163ms、**收回 95ms**。

### 一方掛斷另一方沒掛

串流那行是 `if (call) send('call', call)`。
掛斷之後 `activeCall` 回傳 null，所以**事件根本不送**，
對方就坐在一通已經結束的通話裡，計時器還在跑，直到重新整理。

改法不是「送 null」——null 沒有 id，分不出「你那通結束了」跟
「現在沒有通話」，後者在任何人撥號前一秒都成立，會把正在建立的通話拆掉。
改成送出最近一通的狀態不管結束沒，客戶端比對 id。

**附帶發現**：瀏覽器當掉或強制關閉不會送出結束的 PATCH，那一列會永遠停在
ACTIVE——而一個對話只允許一通進行中，所以那一列會讓之後**每次撥號**都收到
「已經有一通進行中的通話」，介面上沒有任何地方清得掉。
我自己的測試就留下了一筆這種殘留，正好撞到。

## 通話：從完全不通到確認需要 TURN

這是今天最長的一條線，而且**全靠實測推進**，我沒辦法單機驗證。

1. **第一版完全連不上**。接聽方收到 `offer` 時還沒建立 peer（要按接聽才建），
   `handle()` 直接 `return` 丟掉它——而訊號已經從資料庫刪了（投遞即刪）。
   握手永遠不會開始：電話會響、能接、計時器在跑、資料庫寫下「通話 40 秒」，
   **但兩邊沒有任何聲音畫面**。使用者的通話紀錄正好是這個形狀。

2. **視訊沒畫面**。本地預覽的 `<video>` 只在 active/connecting 時渲染，
   但 `srcObject` 是在 ringing 階段設的，那時 ref 是 null。
   鏡頭燈會亮、track 在流、畫面全黑。

3. **修好之後的診斷**：`sig=stable ice=disconnected host=2 srflx=1 relay=0`
   —— `sig=stable` 表示握手成功了，剩下的是真的穿不過 NAT。

4. **做了 Cloudflare TURN**：填兩個環境變數就自動生效，長期 key 只留在
   伺服器端，瀏覽器拿到的是後端 mint 的 6 小時短期憑證。
   費用 $0.05/GB、前 1000 GB 免費，而且只在點對點失敗時才用到。

**還沒驗完**：使用者要去 Cloudflare 開 key（Z103）。

## 補做：AI 助理搬出共用對話（Z106／Z107）

日誌寫完之後你問「AI 助手在哪」，然後說「單獨弄出來，不要在同一個對話內」。
那是對的，而且理由比位置更深。

### 為什麼它不該住在兩個人的對話裡

1. **讀者不同。** 問模型的話跟跟暖寶說的話在同一條捲軸、同一個搜尋結果、
   同一個未讀數字裡。
2. **上下文不同。** 規格要求它「只讀自己那幾輪」，而共用一條對話時，
   唯一的分辨方式是正則比對訊息開頭是不是 `@` 或 `/`——
   **所以每一句沒加 handle 的追問，它都讀不到。**
   那不是保護隱私的代價，那是功能壞掉。
3. **歷史不同。** 一條對話串應該是一個題目；兩個人的對話是永不結束的流水帳。

### 做法

`/assistant` 自己一頁，側邊欄自己一個項目。每人可以開多條對話串，
一條就是一個題目，可以改名、刪除。進去直接打字就是對它說，不用 `@`。

底層沒有第二套實作：對話列多一個 `kind`（DIRECT／ASSISTANT）跟 `owner_id`，
訊息、附件、收回、編輯、搜尋、歷史分頁全部共用原本的 `lib/chat.ts`。

**守衛特別寫了一個 `assertOwnThread`，比成員資格嚴。**
因為我自己也是兩人對話的成員——光檢查成員資格擋不住
「把 DIRECT 的 id 丟進 run 跑一輪」。實測回 403。

「訊息」那邊打 `@助理` 或 `/` 會跳一行提示指去新頁面。
以前會動的東西現在不動了，就要說它搬去哪，不能默默沒反應。

### 指令重新設計

原本六個，其中 `/rewrite` 是錯的——它把「改情節」跟「改文字」混成一個，
而這兩件事要給模型**相反**的指示。一個指令等於每次都在猜使用者要哪一種。

拆成九個 ＋ `/help`：

| 只看（不產生提案） | 會提案 |
|---|---|
| `/ask` 問一件事 | `/write` 寫或續寫正文，可以動情節 |
| `/find` 在作品裡找東西 | `/polish` 潤稿，**明確禁止動情節** |
| `/recap` 回顧某幾集 | `/outline` 寫或改分集大綱 |
| `/check` 挑矛盾 | `/character` 補角色設定 |
| | `/world` 補世界觀 |

`/check` 是新的，大概也是最有用的一個：120 集的長度下，
「第 40 集跟第 9 集打架」人自己很難抓，而這正是模型擅長的。它只報告不提案。

右上角加了問號，打開是完整說明，依「只看／會提案」分組，
每條有用法、在做什麼、以及可以直接填進輸入框的範例。
`/help`、輸入框選單、問號面板**三者都從同一個 `SLASH_COMMANDS` 陣列長出來**，
不會改了指令名之後說明還停在舊的。

## 補做這一段又抓到三個

### 1. Drizzle 在 select 清單裡不會加表名——相關子查詢靜默失效

對話串列表要顯示「最後一句話」跟「訊息數」，我寫成相關子查詢：

```ts
where ${messages.conversationId} = ${conversations.id}
```

編出來是：

```sql
where "conversation_id" = "id"
```

**兩個名字都在子查詢裡解析掉了**，等於每一列都在比
`messages.conversation_id = messages.id`。不報錯、不是空結果，
就是一個永遠為假的關聯——每條對話串都顯示「還沒說話」、訊息數 0。

Drizzle 在 **`where` 子句裡會**加表名（`"conversations"."kind" = $1`），
在 **select 清單裡不會**。所以同樣的寫法在這個專案其他地方是對的——
我逐一查過 `asset-browser.ts`、`episodes.ts`、`usage.ts`、`writing.ts`，
它們不是有 join（會加表名）就是寫在 where 裡，都沒問題。

改成三個查詢：主表 + `group by` 算數量 + `distinct on` 取最後一句。
是測試抓到的，不是我看出來的。

### 2. 懸浮球蓋住送出鍵

助理頁面的送出鍵在右下角，懸浮對話球也在右下角。
**手機上球幾乎整個蓋住送出鍵**——字打得進去，按鈕按不到。

藏掉球不是答案：它是來電會響的地方，而「只有正在看那一頁才會響」
正是前面剛修好的 bug。

改成頁面把自己底部工具列的高度寫成 `--dock-height`，懸浮元件讓開。
用 `ResizeObserver` 即時量，因為輸入框可以拉大。
其他頁面沒設這個變數，行為完全不變。

### 3. `/help` 回報「花了錢」

`/help` 是固定文字，根本不會進模型。但它原本在 `runAssistant` 裡提早 return，
而路由對任何進到 `runAssistant` 的東西都標 `spent: true`。
錢沒花，但那個旗標是給介面判斷要不要顯示費用的，它說的是假的。

把 `/help` 移到路由，跟「打錯的指令」放在一起——兩條免費路徑現在在同一個地方。
實測兩條都 `spent=false`。

順帶修掉：打錯的指令不再被拿去當對話串的標題
（測的時候真的出現一條叫「第四集」的對話串，來源是我打錯的 `/outlinee 第四集`）。

### 測試留下的東西都清掉了

助理的測試對話串全刪。兩人對話裡那一則測試訊息——
收回只是把 `body` 清空留著列，所以它會在你們的對話裡顯示「訊息已收回」——
直接從資料庫刪掉，序號歸零。

## 再補一個：朗讀讀兩三段就停掉（Z108）

你問「朗讀為什麼讀兩句就不讀了」。

### 兇手是那個防呆

程式裡有一段 keepAlive，每 10 秒對語音佇列做一次 `pause()` + `resume()`。
那是業界繞 Chrome 老毛病的標準寫法——Chrome 會把**單一** utterance 砍在 15 秒。

問題是：**這本小說根本沒有那種長度的 utterance。**

量了真實的第一章：

| | |
|---|---|
| 段落數 | 238 |
| 每段字數 | 最短 2、中位 12、最長 43 |
| 語速（Chrome 實測） | 70 字 = 18.3 秒，約 **3.9 字/秒** |
| 一段要唸多久 | 中位約 **3 秒** |

沒有任何一段接近 15 秒。所以那個繞法沒有要修的東西，只剩副作用——
在某些平台的**本機**語音上，`pause()` 落在兩段之間就再也 resume 不回來。

而它第一次觸發是在第 **10.0** 秒。真實文本讀完兩段是第 **13.8** 秒。

> 「讀兩句就不讀了」。時間完全對得上。

### 我沒能在這台機器上重現

這裡的 headless Chrome 只有 Google 的**雲端**語音，而雲端語音吃得下 pause/resume——
我跑了四個情境它都好好的。你那邊用的是 Windows 本機中文語音，
那正是這個毛病被回報的地方。所以這是「證據很強的推論」，不是「我重現了」。

### 所以改法不是換一個繞法

**不要去戳一個正在正常運作的佇列。** 然後加看門狗：
偵測到「既沒在唸、佇列也空著、而且已經兩秒」就自己往下一段走。
這樣不管 `end` 為什麼沒送到——GC、pause 卡死、15 秒砍斷、還是我沒想到的——都救得回來。

修不完所有的 Chrome bug，但可以讓它們都不致命。

### 用實測證明有差

把第 3 個 utterance 的 `end` 事件故意吞掉（在瀏覽器裡 monkey-patch
`speechSynthesis.speak`，打包的是**真正的** `src/lib/speech.ts`，不是抄一份）：

| | 結果 |
|---|---|
| 舊版 | **唸到第 3 段就停住** ← 就是回報的症狀 |
| 新版 | 8 段**全部唸完**，那一段多花 2 秒 |
| 新版（不動手腳） | 8 段全部唸完 |

### 順手修掉的三個

1. **utterance 可能被 GC 掉。** 它只有瀏覽器內部佇列指著，Chrome 會回收它，
   回收之後 `onend` 永遠不來。現在抓著參考不放，停止時再把事件處理器拆掉。
2. **highlight 會錯位。** 它用 chunk 的序號去對段落，只有在「一段剛好等於一塊」
   時才對。只要有一段長到被切成兩塊，之後整章的 highlight 都往後偏，
   而且偏差只會愈來愈大。現在每一塊自己記得屬於第幾段。
3. **按下播放會重排版面。** 朗讀時整頁是用 chunk 重新 render 的（為了讓
   highlight 精確到句子）。現在塊變細了，這樣做會讓文章在你按播放的瞬間碎掉。
   改成一直都 render 真實段落。這本小說一段多半就是一句對白，差別很小。

### 還有一條測試是假的

`tests/novel-export.test.ts` 有一條叫「沒有標點的長段落也會被切開」，
而它只驗了「字沒有掉」——舊程式把 500 字原封不動丟給合成器，照樣通過。
那段要唸兩分多鐘，正是會被瀏覽器中途砍掉的長度。

這幾條本來就不屬於匯出，一起搬到 `tests/speech.test.ts`，
並且改成驗它名字說的那件事。

## 最後一個：刪除章節（Z109）

你問「小說編輯是不是還沒有刪除章節的功能」。沒有——API、lib、UI 三層都沒有，
章節只能新增跟修改。

### 唯一重要的設計決定

**備份是刪除的一部分，不是旁邊的一個選項。**

這跟 AI 助理的提案走同一條規矩，而且理由更強：助理要覆蓋什麼，你至少看得到
diff；自己按下刪除，什麼都看不到。

所以刪之前先把整份文件存進版本紀錄，標籤寫「刪除章節前：〈章名〉」。
`restoreVersion` 本來就會用**原本的 id** 把章節塞回去，所以還原之後
任何指著那一章的東西還指得到。實測刪掉第二章再還原，id、標題、正文全部回來。

### 為什麼一定要在同一個 transaction 裡

`snapshotDocument` 原本自己開 transaction，我把它的本體抽成一個吃 `tx` 的函式，
因為備份跟刪除分兩個 transaction 做的話：

- 備份 commit 了而刪除 rollback → 版本紀錄留下一筆「刪除章節前」，而那一章還在
- 刪除 commit 了而備份 rollback → **章節沒了，沒有快照可以還原**

第二種是這整個功能最不能發生的事。

### 順便處理掉的

- **章號不留洞。** 刪掉第一章之後剩下的往前補，不然側邊欄會讀成 01、02、04
  ——它是直接把 `sortOrder` 當章號顯示的。
- **總字數重算，不是減差值。** 會飄的總數比慢一點的查詢糟。
- **帶 `?revision=`，跟存檔同一套樂觀鎖。** 把暖寶正在打的那一章刪掉，
  跟覆蓋她的段落是同一類意外，所以同樣回 409。

### 測試抓到一個我自己的 bug

跑真的 HTTP 驗這條路由時，第三項「完全不帶 revision」回的是 **409**，不是 400。

原因是 `Number(null)` 等於 `0`，而 0 是一個完全合法的 revision，
所以忘記帶參數的請求會滑過我的檢查、去撞樂觀鎖，然後回「這一章剛剛被改過」。

**那是在怪別人，而實際上是少了一個 query string。** 改成先檢查參數在不在，
再轉成數字。

五項全過：過期的 revision → 409、沒帶 → 400、正常刪除 → 200 並回報備份版號、
再刪一次 → 404。

### UI

章節列 hover 或鍵盤 focus 才出現垃圾桶——這是一份你整天點來點去的清單，
一個永遠停在每個標題旁邊的刪除鍵，離失手只差一次。

按下去是就地兩段式確認，不是 `confirm()` 對話框：瀏覽器對話框會卡住整頁，
而且讀起來像瀏覽器在警告你，不是這個 app 在問你。
之所以敢不用強制性的 modal，是因為它本來就救得回來，而確認那行字就是這樣寫的。

### 測試留下的東西清掉了

驗證過程在版本紀錄留了兩筆「刪除章節前：＊＊測試用＊＊」，已經刪掉，
文件版本號回到 v4。EP001 的正文 3,198 字完好。

## 補做：製片中心（Z127）、卷與章節落點（Z128）

### 「製片中心只是一堆排程那沒必要特別做」

你說得對。一頁有狀態的清單就是個圓角的資料庫客戶端。製片中心該回答的是
任何單一筆紀錄回答不了的問題，所以改成六個分頁：待確認、體檢、批次生成、
花費、產能、佇列。預設停在「待確認」。

**做完才發現，體檢的第一條根本不是哪一集的問題。**

第一版跑出來 18 條警告。看起來很豐收，其實是兩件事重複了九次——每一集都在
抱怨「原著篇幅超過目標片長」。真正的事實只有一句：

> 單集目標字數 4,000、目標片長 150 秒。4,000 字朗讀約 17 分鐘，
> 150 秒大約裝得下 585 字。這兩個設定不可能同時成立。

這跟那次 `NOVEL_TO_SCRIPT` 跑完、模型自己在草稿裡抱怨的是同一件事，只是它
當時只能對那一集說，而且說在一份沒人會翻開的草稿裡。所以體檢改成
**一個事實一條**，集數收進那一條的內文（`EP002–EP009`），不是變成九條。
18 條變 5 條，每一條都是不同的事。

《一灶見山河》順帶被量出來：已寫的 7 集平均 8,351 字，是自己目標 4,000 字的
209%。

### 「捨棄」原本根本不存在

這是那兩份大綱躺一天沒人動的另一半原因。`requestCancel` 只收 QUEUED /
RUNNING——這是對的，「取消」的意思是停下正在做的事，而待確認的任務已經做完
了，沒有東西好停。但那表示**不想要的產出只能永遠留在待確認**。

加了 `discardCandidate`，狀態轉 CANCELLED，但**產出內容留著**：它花了錢，
而且模型那句「資料不足以寫出 EP001，若硬寫就得自行虛構」是當天最有用的一
句話。「捨棄」是對小說的決定，不是銷毀證據的要求。

### 採用要先看過全文

`aiApplySchema` 有個 `acknowledge: true`，註解寫著「確認使用者看過自己要覆蓋
什麼」。收件匣如果直接把它填上去送出，那個欄位就變成一句謊話。所以採用按鈕
要抓過完整內容之後才會開。

### 批次：全 app 唯一一按就會花錢的畫面

所以是兩按。**先試算**：伺服器列出範圍內每一集，要跑的說為什麼要跑，跳過的
說為什麼跳過（「已經有一份產出在等確認」／「這一集還沒有小說內容」），估價
是每集真實估算的**總和**——不是一集乘以 N，EP004 是 EP001 的三倍長。
**再送出**：伺服器重新試算一次，因為畫面上那份清單是幾秒前的，這幾秒裡暖寶
可能已經從她的編輯器下了同一筆。

實測 EP001–EP012 的 `NOVEL_TO_SCRIPT`：8 集要跑、4 集跳過、估 $1.6401。

### 路上兩個真錯誤

- `where kind <> ''` 在列舉欄位上**不是 false，是 22P02**。本來是要過濾
  `model` 那個可以是空字串的文字欄位，順手套到 `kind` 上就炸了。
- `c.tier in ('LEAD', 'MAIN')` 的 `MAIN` **根本不存在**。枚舉只有
  LEAD / SUPPORTING / MINOR / EXTRA。憑印象寫枚舉值的代價。

### 卷：原本就有，只是沒有介面

你要「多一個卷這個單位」。查下來 `arcs` 從第一支 migration 就在，每一集的
`arc_id` 本來就是 NOT NULL，兩部作品各有一個「第1部」裝著全部 120 集。

所以**沒有新開表**。再做一套平行的分組，等於讓每一集有兩個會互相矛盾的父層。
少的從來不是資料，是「能再做一個」的介面。

你說「不要影響到原來劇本的對接跟其他數據」。這句話在這個 schema 裡有三個
具體的地雷：

1. **`number` 的註解寫著「第幾集 within the arc」。** 那句只有在每部作品
   一卷時才成立——而現在可以有很多卷了。照著那句話去實作，搬卷就會重編號，
   小說、劇本、分鏡和正文裡每一句「第 007 集」全部對不上。註解已經改掉，
   而且寫明了為什麼。
2. **`plannedEpisodes` 是跨卷加總的。** 新卷若吃 schema 預設的 120，作品
   卡片上的「規劃 120 集」會無聲變成 240。新卷一律從 0 起算。
3. **`episodes.arc_id` 是 `on delete cascade`。** 真的 DELETE 一個卷會把
   裡面的集數一起帶走。所以刪卷是：同一個 transaction 裡先把集數搬走、
   沒地方搬就直接拒絕、最後一卷不准刪，而且卷本身只做 soft delete。

測試盯的就是這三條，不是 CRUD。

### 一個差點混過去的測試

「最後一卷不准刪」第一版寫成 `if (listed.length !== 1) return`。前面的測試
留下了卷，所以它**永遠綠燈但什麼都沒斷言**。改成自己先把前置狀態清乾淨再
斷言——跟之前 `projects.test.ts` 那次是同一種病。

### 新增章節：在這一集還是下一集

寫完一章常常就是在決定它屬於這一集還是下一集，而原本那顆按鈕永遠替你答
「這一集」，你要翻到下一集才發現。

兩個去處走不同的路：「這一集」打開著的文件、原地加進清單、不換頁；
「下一集」走以集數為鍵的新路由，因為**下一集可能還沒有小說文件**，前端拿不
到一個不存在的 id——這個決定沒辦法在前端做。而且找的是下一個**真的存在**的
集數，不是 `number + 1`：集數是整批建的，中間有洞是正常的。

測試庫裡有 74 集沒有小說文件，所以「會自己開一份」那條確實跑得到。

## 又弄壞一次：換行

用 Python 回寫 `TODO.md` 之後，`todo-milestones.ts` 算出 **0 / 0**，而且
**把那個 0 / 0 寫回了檔案**。

Python 的文字模式寫入會把 `
` 轉成 `os.linesep`，在 Windows 上就是 CRLF。
而腳本用 `text.split('
')` 切行，正則又以 `$` 結尾——殘留的 `` 是
JavaScript 正則裡的行終止符，`$` 過不去，於是**每一個標題都靜默地比對不到**。
不是報錯，是安靜地算出 0。

修在腳本：改成 `split(/?
/)`。這才是耐用的修法——這個 repo 的
`core.autocrlf` 是 `true`，工作區本來就可能是 CRLF，腳本不該依賴它。

順手把 66 個檔案「改回 LF」是個過度反應，`git diff --ignore-cr-at-eol`
確認只有 TODO.md 有真正的內容變動，其餘已還原。
