**那是推論，不是量測。** 實際拆掉修法再量一次：

| 我說的 | 實際 |

## Z199：分鏡的「0 鏡」

drizzle 渲染內插進 `sql` 模板的欄位物件時，**加不加表名要看上下文**：

| 形狀 | 渲染 |
| --- | --- |
| 單表 select（沒有 join） | `"id"` ← 會出事 |
| `where` 子句裡 | `"episodes"."id"` |
| select 但有 join | `"assets"."id"` |

第一種的子查詢裡，那個光禿禿的 `"id"` 綁到最內層那張表——它也有 `id` 欄。條件變
成 `s.episode_id = s.id`，永遠不成立。**Postgres 不報錯，它只是回 0**。

真正壞的兩處：`storyboardIndex` 的四欄（鏡頭數／秒數／已核准／有無劇本），
`listOutline` 的每集字數。

兩道鎖：`check:subquery` 擋寫法（只抓被比較的那一側、只認從 schema import 的名
字，不然 `unnest(${projects.tags})` 的標籤搜尋會被誤報），
`tests/subquery-counts.test.ts` 守數字。兩個都做過破壞驗證。

## Z201：雙視角審核的「編劇那一趟」

老闆那份 mockup 裡**唯一做不出替代品**的東西。它自己的最後三行寫著：

> 雙視角必須先執行完全隔離未來資訊的觀眾審核，再由編劇視角判斷疑問是否已有合理
> 解釋。**不得讓觀眾階段接觸隱藏設定。**

在一個複製貼上的工具裡，那只能是一句**請求**——同一個對話框裡模型早就讀過答案
了，叫它假裝不知道是禮貌。在這裡它是結構上做不到的，三道：

1. **隱藏設定自己一張表**（`episode_secrets`），不是 `episodes` 的欄位。長在
   `episodes` 上的欄位會被每一個 `select *` 帶出去。順帶一提 `episodes` 本來就有
   一個 `notes`（製作備註）——**連名字都會打架**，而「哪一個 notes」這種問題在
   code review 上看不出來。
2. **兩次獨立的呼叫。** 觀眾那一趟的 context 物件裡根本沒有那一欄，而且它拿不到
   編號比這一集大的任何東西。
3. **`renderContext` 在觀眾視角遇到 `secretNotes` 直接丟例外。**

第三道才是保證，前兩道是習慣。下一個人多傳一個欄位進來，外洩會悄悄發生，而產出
**看起來完全合理**：模型知道答案，所以它說這一集沒有問題。

`tests/audit-isolation.test.ts` 五條守這件事，其中一條**專門擋「改成靜靜略過」這
個比較溫和的修法**——那個修法會讓測試安靜地通過，而產出是一份模型知道答案的報
告。破壞驗證：拿掉 throw，兩條紅。

### 四種判定的顏色

「合理留白」是**綠的**，因為那是一個**不用改**的結論。第一版四種同一個灰，整份報
告讀起來像四十條待辦——而懸疑本來就要留白，觀眾在那裡有疑問正是要的效果。

沒填隱藏設定也判得了，但畫面會說清楚它也不知道後面會怎麼寫，多半落在「資料不
足」。不要讓人以為那是一個有把握的結論。

### 活動紀錄裡不寫內容

動態是兩個人互相看對方做了什麼的地方，而隱藏設定正是不該被順手看到的東西。寫
「改了隱藏設定」就夠了——寫一段摘要等於把劇透貼到儀表板上。有測試守著。

### 順手修掉：VIP 通道的錯誤會變成 500

供應商說的是「額度不夠」，畫面顯示「伺服器發生錯誤」。排佇列那條路上失敗會留在
`ai_jobs` 上、連供應商那句話一起顯示在 AI 製片中心；**VIP 通道沒有那張工作列**。

現在四種有明確動作的（額度、限流、金鑰、滿載）加一句中文，**原話照樣附上**：翻譯
是方便，真要查的時候原話才是能拿去搜尋的那一個。而且訊息截到兩百字——供應商的錯
誤訊息偶爾會把整個請求回放一遍，而那裡面有這部作品的正文，一個錯誤提示不該變成
一次外洩。

### 門檻又幫我抓到一次

`check:dead` 報了三個「今天長出來、沒人用」的匯出。兩個是我多匯出的（收回成私
有），第三個 `secretEpisodeIds` 是**我寫了忘記接**——現在接上了，每一集的設定區標
「已填／還沒填」，而且**只傳 id 不傳內容**：把那段劇透送進每一次頁面載入，正是這
整個功能在防的事。

基準線順手重寫，diff 是 **+1 −5**：新的那個測試用匯出進去，五個昨天做成本中心時
真的接上的出來。它變準了，不是變鬆。
