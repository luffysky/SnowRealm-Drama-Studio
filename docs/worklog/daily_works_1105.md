## 我今天寫錯的東西

### 1. 我把一句假話寫在五個地方，而且講給了你

Z167 做角色多圖的時候，我在註解、UI 提示文案跟一個吐司裡都寫了：

> 分鏡與 AI 生圖讀的就是 `key_visual_asset_id`

**那不是事實。** 全專案 grep 之後：AI 拿角色的是 `name` / `tier` /
`appearance` / `personality` 四個**文字**欄位（`ai/jobs.ts`），
`CHARACTER_DESIGN` 也只寫文字欄位；分鏡的參考圖是 `shots.ref_asset_id`，
由使用者自己挑，**沒有任何地方從定妝照帶過去**。唯一讀它的是角色列表與
角色面板的 `Portrait`。

程式行為是對的——移掉定妝照確實要有人遞補，因為那兩個地方真的會變。
**錯的是理由。** 而錯的理由有兩個後果：下一個人會照它去推論別的設計，
以及它會變成騙人的 UI 文案（spec 說「文案要是事實」管的就是這個）。

這一條我已經加進記憶：**宣稱一個下游消費者存在，跟宣稱一個欄位存在是同一
類主張**，一樣要查。

## 三支工具自己都錯過，而且錯的方向都一樣

**三支都是「把有在用的報成沒人用」。**

`check:api` 錯了三次：方法藏在 `put()` 輔助函式裡、方法由三元運算決定、
網址樣板字串跨行又含空白。

`check:ai` 第一版**自信地胡說**：回報 `NOVEL_TO_AUDIO 經由
/api/ai/jobs/*/cancel`。取消一個任務當然不是發動它——而通用端點與生命週期
端點會碰到每一種任務，用它當證據這支工具會永遠報「全部接好了」。

`check:client` 第一版對七個正常檔案報錯，因為沒分辨 `import type`
（編譯時就抹掉，不會進 bundle）。

這三組全部變成永久的自我檢查。理由是同一句：
**一份充滿假警報的清單比沒有清單更糟，因為它會讓人以為自己檢查過了。**
而一個會對正常程式碼報錯的檢查，第二天就會被當成雜訊關掉。

（`check:api` 還差一點刪錯一個：`/api/search/reindex` 確實沒有任何介面
呼叫，因為它是 `vercel.json` 裡每天 03:30 的排程。豁免清單現在**從
`vercel.json` 讀出來**，不是手寫的——手寫的會過期。）

## 今天最貴的一個 bug：一行 `?? 'high'`

症狀是「小說轉劇本每次都失敗」：

```
stop_reason=max_tokens, 區塊=thinking, in 4810 / out 8000, 零內容
```

三次全軍覆沒，**照樣收錢**。

根因是 `enqueueJob` 的這一行：

```ts
effort: input.effort ?? 'high'
```

介面從來不送 effort，所以**每一個**進佇列的任務都被蓋上 `'high'`，
而 `request.effort` 在適配器的優先序裡排第一——於是 Z22 做的 `TASK_EFFORT`
跟系統設定那張任務設定表，**兩個都從來沒有被讀到過**。
查佇列最近十筆，除了有聲書（不走這條路）以外**每一筆都存著 high**。

而 `max_tokens` 在 adaptive thinking 底下是**思考加正文的總額**，
不是正文的額度。被強制 high 思考的「改編一整集小說」就這樣把 8000 全花在
思考上。

**一個預設值替人做了決定，而「人沒選」跟「人選了 high」在資料上長得一樣。**

修法是佇列不再替它決定（沒指定就存 null，讓優先序去回答），優先序抽成純
函式並且有測試盯著。然後 Z160 在同一個地方又抓到一次：
`model_assignments.effort` 是 `not null default 'high'`，
**指派過一次模型的任務就又讀不到那張表了**——同一個 bug 換一扇門。
改成 nullable。

### 「做了比不做糟」一天出現四次

這是今天最值得記下來的一類。它不是「沒做」，是**做了之後比原來更壞**：

- **備註輸入框會把 `completed_at` 洗掉。** Z165 讓備註順便把「現在的狀態」
  一起送回去，於是在一個已完成階段的備註框打字，等於重新宣告一次「設成已
  完成」：完成時間被蓋成今天、活動紀錄多一筆假的狀態變更。而且 zod 會
  `.trim()`，不受控的 `defaultValue` 不會跟著更新，**之後每一次失焦都再送
  一發**。
- **作品卡選單改成往下開，被切掉的比往上開更多。** 裁切的是祖先卡片的
  `overflow-hidden`，不是選單自己的 `max-h-48`。按鈕下方到卡片底只剩約
  70px，上方還有 170px 以上——我把看不見的從一兩項變成五項。
  而且把 `<Link>` 換成 `<button>` **沒有達成註解寫的任何一個目的**：
  `<button>` 同樣是 interactive content，`<a>` 的內容模型一樣禁止，
  只是順便把中鍵開新分頁和 Ctrl 點擊弄壞了。
- **超大圖的空白偵測會誤殺去背 PNG。** 只抽左上角 64×64、只看 alpha，
  而去背人像的左上角本來就是透明的：一張 800KB 的小圖完全無法裁切，
  錯誤訊息還說它太大。
- **`router.refresh()` 沒有回 Promise，而 `busy` 在 `finally` 就放掉了。**
  移除一張角色圖之後 RSC 還在路上，縮圖列上它還在、按鈕也能按——
  點它就會把連結**重新插回去**：剛做的移除被無聲還原，那張圖還變成了定妝照。

## 一個反覆的修法：讓它只有一個地方可以改

今天有五條的修法是同一句話，而且錯法也是同一句話：**兩邊各自寫一次，然後
安靜地對不起來。**

| 錯 | 修法 |
| --- | --- |
| `estimate()` 用 8000、`run()` 用 16000——而報價餵給預算閘門，**上限被系統性低估，一批任務可以集體超支** | `ceilingFor()` |
| `/api/ai/estimate` 回 `{ estimate: {...} }`，兩個呼叫端讀兩個不存在的欄位——**預估成本一直是零**，而零不會觸發錯誤處理 | 共用 `AiEstimateResponse` |
| 懸浮面板的 `max-height` 寫死 5rem，`bottom` 是動態的 | 兩個值共用同一個算式 |
| 階段狀態有兩個寫入點，Z165 只修了單筆那個 | `stageStatusPatch()` |
| 99 上限在單筆路徑、`greatest()` 在重算路徑，**夾到 99 會被重算推回 100** | `capped` CTE 算一次，`set` 與 `where` 都讀它 |

「記得兩邊一起改」不是修法。

## 兩件我用量測而不是用眼睛解決的事

### 懸浮面板跑到畫面外

`scripts/probe-floating-panel.mjs` 量 `getBoundingClientRect()` 的四個邊。
修之前 844×390 與 1280×420 兩種尺寸 `top=-10`，修之後 `top=8`。

所以 probe 還要先把面板撐高才量得到。

### Azure `<phoneme>` 到底吃什麼

實測矩陣，不是查文件：zh-TW 吃注音（`ㄏㄨㄢˊ`），zh-CN 吃拼音但**聲調數字
前面要有空格**（`huan 2`，寫成 `huan2` 回 400），zh-HK／yue／wuu／
multilingual 整個拒收。39 支華語聲音裡 35 支真的照做、4 支收下但忽略。

驗證用**位元組長度差**而不是雜湊：Azure TTS 不是決定性的，同樣的輸入雜湊也
會不一樣，所以「雜湊相同」證明不了任何事。

## 一件事值得單獨提：那把 token 寫在雲端排程的提示裡

`HEALTH_TOKEN` 那把金鑰目前以明文寫在每日健康檢查排程的提示文字裡
（`trig_012rGMESLrAntMybpMZQJ1Lk`）。它只開一道唯讀的門、**刻意不共用
`CRON_SECRET`**（那一把同時開著 `/api/ai/worker`，而它會花錢），
所以洩漏的後果有限。

但它仍然是一把金鑰放在一個不是秘密管理的地方。等你在 Vercel 設好環境變數、
確認排程跑得起來之後，值得換一把新的、並且改用排程的環境變數欄位。

> **11-08 補記：** Vercel 已經設好了，而排程**仍然跑不起來**——原因從頭到尾
> 就不是 token（見 Z177）。那把金鑰也因為查這件事而又被讀出來一次，所以
> 「換一把新的」現在不是「值得」，是**該做**。

## 兩條沒有編號的債（寫在這裡免得忘記）

- **`production_progress_events` 全專案沒有寫入端。** 製作進度趨勢圖讀它，
  所以那張圖**永遠是空的**——而空的圖看起來像「這段時間沒有進度」，
  不像「這個功能沒接線」。
- **`episodes.coverAssetId` 沒有寫入路徑。** 集數詳情頁的主視覺區讀它，
  而沒有任何介面寫得進去，所以那裡**永遠是佔位圖**。
  Z65 做的是作品封面，不是集數封面。

這兩條跟上面那張清單上的 `voiceStyle`、`model_assignments` 是同一個病。

**而 `check:dead` 現在抓不到它們**——我原本在這裡寫「基準線裡本來就記著」，
查了之後不成立：`scripts/dead-wiring-baseline.txt` 那 172 行**每一行都是
`src/lib/<檔>.ts#<匯出名>`**，裡面沒有任何欄位。那支工具的欄位規則是
**「全專案沒有任何地方提到」**，不是「沒有人寫」——而 `episodes.coverAssetId`
有八處以上在讀它，所以它永遠不會出現在輸出裡；`production_progress_events`
也只有 `stageId` 單一欄位被點出來，不是「沒有寫入端」這件事。

**這正是這份日誌自己在罵的那種錯：宣稱一個工具在盯著它，而沒有去查那支工具
到底盯什麼。** 要嘛接線，要嘛另外加一條「有讀取端但零寫入端」的規則——
而後者才是這一類 bug 真正的形狀。
