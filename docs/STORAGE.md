# 儲存與壓縮

R2 的帳單長什麼樣，為什麼圖片存兩份，為什麼影片不壓。

---

## 1. 先把帳單結構講清楚

擔心「檔案太大會讓 R2 帳單秒爆」是合理的直覺，但 R2 的計費結構跟 S3 不一樣：

| 項目 | 價格 |
| --- | --- |
| 儲存 | 約 **$0.015 / GB·月**（每月前 10 GB 免費） |
| **對外流量（egress）** | **$0.00** |
| Class A（寫入、列表） | $4.50 / 百萬次（每月前 100 萬次免費） |
| Class B（讀取） | $0.36 / 百萬次（每月前 1000 萬次免費） |

套到這個專案的規模：

- 120 集成片，1080p 約 75 MB/集 → 約 **9 GB** → **$0.14/月**
- 加上 AI 中間素材、每一版都留（規格要求新版不覆蓋舊檔），抓 200 GB
  → **約 $3/月**
- 要到 1 TB 才 $15/月

**結論：該怕的不是「單一檔案太大」，也不是「被下載很多次」（流量免費），
而是「版本無限累積」。** 成本是線性的，不會突然爆掉；會爆的是沒有人在看
總量的時候，三個月後發現存了 5 TB。

> 所以 `docs/SEARCH.md` 式的省錢手段（hash 擋重算）在這裡的對應物是
> 「看得到用了多少」。素材面板會顯示總量與估算月費。

---

## 2. 「壓縮後畫質不變、檔案變小」做不到

兩件事要先分清楚：

**（a）泛用壓縮（zip / gzip / brotli）對媒體檔幾乎沒用。**
JPEG、PNG、MP4 本來就是壓過的格式，再用 zip 包一次大約省 0–2%，
卻多了一道解壓手續。不要做。

**（b）真正有效的是「重新編碼」，而那是有損的。**

| 做法 | 省多少 | 畫質 |
| --- | --- | --- |
| PNG → 無損 WebP | 10–25% | 位元完全相同 |
| PNG → AVIF/WebP 品質 82 | **80–90%** | 肉眼看不出，但不是位元相同 |
| H.264 → AV1 | 約 50% | 有損，而且要 ffmpeg |

另外：**AVIF / WebP / AV1 不需要「解壓」。** 瀏覽器直接解碼，
沒有「用到的時候再解開」這個步驟。會需要解壓的只有 (a)，而 (a) 沒用。

---

## 3. 所以實際做法：母片 ＋ 預覽檔

圖片存兩份：

| | 用途 | 大小（1920×1080 的 AI 生成圖為例） |
| --- | --- | --- |
| **母片（master）** | 交付、再編輯、放大 | 原樣，約 2.5 MB |
| **預覽檔（PREVIEW variant）** | 介面上所有縮圖、卡片、列表 | WebP/AVIF，約 150–300 KB |

母片**原封不動**——重新編碼不可逆，而交付用的檔案不能是壓過的。
預覽檔由**瀏覽器**產生：瀏覽器手上已經有解碼好的點陣圖，
而 serverless function 要在 60 秒內把母片抓下來、解碼、重編碼才能做到同一件事。

多出來的儲存成本約 10%（預覽檔很小），換到的是：

- 列表頁從「拉 120 張完整 PNG」變成「拉 120 張 200 KB 的圖」，
  **這省的是讀取的量，不只是存的量**。
- 手機上的差別最明顯。

### 流程

```
瀏覽器                                        伺服器
  │  POST /api/uploads ─────────────────────▶ 建 PENDING asset，回簽章網址
  │  PUT 母片 ──────────────────────────────▶ R2
  │  POST /api/uploads/complete ────────────▶ HEAD 確認，標 COMPLETED
  │
  │  （母片已安全落地，以下失敗都不影響它）
  │  makeImagePreview()  canvas 縮圖 + 重編碼
  │  POST /api/assets/[id]/preview ─────────▶ 建 PENDING variant，回簽章網址
  │  PUT 預覽檔 ────────────────────────────▶ R2
  │  PATCH /api/assets/[id]/preview ────────▶ HEAD 確認，標 COMPLETED
```

預覽檔的產生**刻意不納入上傳狀態**。檔案已經傳完了，
預覽失敗只是介面慢一點，不該讓整筆上傳看起來失敗。

### 讀取

```
/api/files/[assetId]                   母片
/api/files/[assetId]?variant=preview   預覽檔，沒有就自動退回母片
/api/files/[assetId]?download=1        母片，帶 Content-Disposition（永遠不給預覽檔）
```

退回母片這件事很重要：預覽檔是最佳化，不是前提。
預覽機制上線前就存在的素材、以及預覽產生失敗的素材，照樣要能顯示。
呼叫端用 `src/lib/asset-url.ts` 的 `assetPreviewUrl()`，不需要知道有沒有預覽檔。

### 不產生預覽檔的情況

- 原檔小於 200 KB（多存一個物件、多一次請求，不划算）
- SVG（本來就小，轉成點陣圖反而失去意義）
- 產出來沒有比原檔小（小圖或已經最佳化過的圖會這樣）
- 瀏覽器不會編碼 AVIF 也不會編碼 WebP（實務上不會發生）

以上每一種都是「沒有預覽檔」，不是錯誤。

## 4. 影片不壓

成片本來就是 H.264／H.265，已經壓過了。再壓一次：

- **瀏覽器端做不到。** ffmpeg.wasm 跑一支 3 分鐘的片要好幾分鐘，
  而且要先載入十幾 MB 的 wasm。不實用。
- **伺服器端要另外一個服務。** Vercel Hobby 跑不動 ffmpeg，
  而且轉檔的運算費大概率比省下來的儲存費貴——120 集成片總共才 9 GB，
  省一半是省 $0.07/月。

所以影片原樣上傳。真要省，在本機先用 ffmpeg 壓完再上傳：

```bash
# AV1，視覺上接近無損，檔案約剩一半（慢）
ffmpeg -i in.mp4 -c:v libsvtav1 -crf 30 -preset 6 -c:a copy out.mp4

# H.265，快很多，省約 30%
ffmpeg -i in.mp4 -c:v libx265 -crf 26 -preset medium -c:a copy out.mp4
```

## 5. 大檔案上傳

超過 64 MB 自動走分段上傳（multipart），位元組直接從瀏覽器進 R2，
不經過 serverless function——否則會同時撞上請求大小與執行時間的限制。

R2 的硬限制：

| 項目 | 上限 |
| --- | --- |
| 單一物件 | 約 4.995 TiB |
| 單次 PUT | 約 4.995 GiB |
| 分段數量 | 10,000 |

分段大小會依檔案大小調整，所以不會出現「檔案超過 10,000 段上限」這種
人為天花板。單一分段失敗會重新簽章並只重傳那一段，不是整個檔案重來。

`MAX_UPLOAD_BYTES` 仍然存在，但那是防手滑的欄杆（不小心把 500 GB 的
素材庫拖進來），不是技術限制——要調就直接改。
